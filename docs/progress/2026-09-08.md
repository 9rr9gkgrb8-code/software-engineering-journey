## What I learned

1. **Security boundaries are product architecture, not cleanup.** Forge's runtime, browser boundary, student account permissions, and reverse-proxy design must stay constrained even when access becomes easier.
2. **A private beta and a production SaaS are different systems.** A working family-network path is useful evidence, but public hosting still needs real-device acceptance, identity isolation, monitoring, privacy/consent handling, deployment verification, and recovery evidence.
3. **The learning loop matters more than feature count.** The strongest current Forge proof is lesson → attempt → validated response → hint/retry → mastery/progress, not the number of screens or AI features.
4. **Small, reviewable engineering slices reduce risk.** Cloud access, mobile UX, signup, deployment, and readiness evidence should be kept as separable changes wherever possible.

## Article read

Google Engineering Practices: **Small CLs**
https://google.github.io/eng-practices/review/developer/small-cls.html

Main takeaway: one self-contained change per review is easier to reason about, test, merge, roll back, and review thoroughly. Related tests should travel with the behavior change, and refactors should usually be separated from feature work.

## Applied lesson

For Forge, avoid giant "make it cloud-ready" changes. Treat the path as a sequence of independently verifiable slices:

1. mobile shell and accessibility;
2. invite-only student signup;
3. hardened remote deployment boundary;
4. readiness probe and monitoring evidence;
5. real-device learner acceptance;
6. only then expand beyond the private pilot.
